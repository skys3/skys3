## 1. How to read this matrix

- **Supported** means as S3 does it, apart from request headers that ask for a rejected feature (section 4). **Partial** means supported except what its note says. **Not supported** means the operation always answers with the error given, for every caller and every input it parses.
- Operations that no IAM action maps to are denied to every caller (§11), so they answer `403 AccessDenied` rather than `501 NotImplemented`.
- Every answer is the one S3 gives where it has one: for example, Object Lock requests answer as for a bucket without Object Lock, and ACL requests as for a bucket whose object ownership is `BucketOwnerEnforced`.
- Requests are path-style (`https://host/bucket/key`), signed with SigV4 in the `Authorization` header or as a presigned URL. SkyS3 has no regions: a credential scope may name any region, and every bucket answers as one in `us-east-1`.
- Each bucket has a mode, `write_back`, `local`, or `read_only` (§4.1), set when it is created. A few operations depend on it; their notes say how.

## 2. How it is kept current

Every table in sections 3 to 7 is generated by a test that also checks what the table says, and the test fails when the committed table differs from what it generates:

| Section | Generated and checked by | In CI |
|---|---|---|
| 3, 4 | `crates/skys3-gateway/tests/compatibility.rs`: sends a request for every operation `s3s` routes, and every rejected request, through the gateway; checks the operation `s3s` routes it to and the answer | `rust` job |
| 5 | `crates/skys3/tests/sdk.rs` (`rust_sts_operations`): sends every STS action to the node binary | `rust` and `sdk` jobs |
| 6 | `crates/skys3/tests/sdk.rs` with the `s3-tests` client: the subset's results per group, as the pytest plugin `tests/sdk/s3-tests/skys3_s3tests.py` reports them | `sdk` job |
| 7 | `crates/skys3/tests/sdk.rs` (`the_matrix_lists_the_sdk_clients`): the versions the clients' Dockerfiles, lock files, and `Cargo.lock` pin | `rust` and `sdk` jobs |

To regenerate a table after a change, run its test with `SKYS3_UPDATE_DOCS=1`, which rewrites the table instead of failing, and review the difference:

```sh
SKYS3_UPDATE_DOCS=1 cargo test -p skys3-gateway --test compatibility
SKYS3_UPDATE_DOCS=1 cargo test -p skys3 --test sdk
# Section 6 needs the s3-tests client: in its image (tests/sdk/run.sh build s3-tests),
SKYS3_UPDATE_DOCS=1 SKYS3_SDK_CLIENTS=s3-tests cargo test -p skys3 --test sdk
# or on the host, with a checkout of the pinned commit and its requirements:
SKYS3_UPDATE_DOCS=1 SKYS3_SDK_CLIENTS=s3-tests SKYS3_SDK_LOCAL=1 S3TESTS_DIR=<checkout> \
    cargo test -p skys3 --test sdk
```

A failing test also prints the table it expected, so the `sdk` job's log holds section 6 as CI generated it.

## 6. ceph/s3-tests

The SDK matrix runs a selected subset of [`ceph/s3-tests`](https://github.com/ceph/s3-tests) at the commit `tests/sdk/s3-tests/Dockerfile` pins (section 7). Every test at that commit is classified, and the run fails before any test starts if one is not, or if a line of the lists matches no test, so a new commit cannot add or rename tests unnoticed:

- `tests/sdk/s3-tests/subset.txt` selects the tests of features SkyS3 supports, by group. Every selected test must pass: a failure in a supported feature is a bug, never an exclusion.
- `tests/sdk/s3-tests/excluded.txt` excludes the rest, by group, each with its reason: a feature SkyS3 does not support (*Not supported*), a behaviour that differs from what the tests expect on purpose (*Known divergence*), or something the tests assume of the server that SkyS3 is not (*Test-suite assumption*), such as an RGW extension, a second account, or an IAM API.

s3-tests empties its buckets by listing object versions, which SkyS3 rejects; its plugin lists them with ListObjectsV2 instead, and changes nothing else about the tests.

## 7. SDK matrix

The SDK matrix (§16.2, `crates/skys3/tests/sdk.rs`) runs every client at once against the node binary serving HTTPS, with STS on the same listener and an OIDC issuer the node trusts. Each SDK client checks the SDK's default checksum and the five algorithms SkyS3 supports, `aws-chunked` uploads with trailing checksums, multipart uploads, multipart copies by UploadPartCopy, presigned URLs, and web-identity credentials from its default credential chain, configured only by `AWS_ENDPOINT_URL_S3`, `AWS_ENDPOINT_URL_STS`, `AWS_ROLE_ARN`, and `AWS_WEB_IDENTITY_TOKEN_FILE`, refreshed while requests run. The Rust client also checks bucket lifecycle rules and the STS operations of section 5.
